# Account Statement Authentication and Verification Guide

This guide details the security model, authentication requirements, digital signature specification, and third-party audit verification procedures for official monthly account statements generated by `backend/src/routes/statements.js` (Issue #910).

---

## 1. Security & Authentication Requirements

The endpoint `GET /api/v1/statements/:month` produces documents labeled **"Official Monthly Account Statement"**. Generating official financial documents requires strict authentication and authorization:

- **Authentication**: Callers must authenticate using either:
  1. A valid JWT Bearer token: `Authorization: Bearer <jwt-token>`
  2. An Admin API key: `X-API-Key: <api-key>`
- **Authorization**:
  - Regular users can **only** request statements for their own account (`req.user.id === requestedUserId`). Requests attempting to access other accounts are rejected with `403 Forbidden`.
  - Administrators (with `admin` role or valid `x-api-key`) can generate statements across accounts for customer support or compliance audits.
  - Unauthenticated requests are rejected with `401 Unauthorized`.

---

## 2. Digital Signature & Tamper-Evidence Specification

To ensure statements cannot be altered or falsified post-download:

1. **Content Digest (SHA-256)**:
   The structured financial data (balances, fees, trades, dates) is serialized into canonical JSON and hashed using SHA-256 (`dataHash`).
2. **Cryptographic Signature**:
   The data digest is signed using HMAC-SHA256 with the platform's official signing key (`STATEMENT_SIGNING_KEY`).
3. **Embedded Verification Block**:
   The generated PDF document embeds a dedicated verification section displaying:
   - Key Identifier: `rwa-statement-signer-v1`
   - Content Digest: Hexadecimal SHA-256 digest
   - Digital Signature: Base64 signature
   - Timestamp: ISO 8601 issuance timestamp
4. **Binary Tamper-Evidence Headers**:
   Every response includes verification headers:
   - `X-Statement-SHA256`: SHA-256 hash of the complete PDF binary
   - `X-Statement-Signature`: Cryptographic signature of the binary hash
   - `X-Statement-Data-Hash`: SHA-256 hash of the financial content
   - `X-Statement-Key-Id`: Key identifier (`rwa-statement-signer-v1`)

## 3. Third-Party Verification Workflow

Third parties — such as a user's accountant, a lending institution, or a tax authority — can verify that a statement PDF is genuine and has not been altered after issuance.

### Method A: Verification API Endpoint (Online)

Submit the statement's SHA-256 hash or signature to the public verification endpoint:

#### Request (POST):
```bash
curl -X POST https://api.marketplace.example.com/api/v1/statements/verify \
  -H "Content-Type: application/json" \
  -d '{
    "hash": "4a5e8f...",
    "signature": "k9j2F..."
  }'
```

#### Request (GET query):
```bash
curl "https://api.marketplace.example.com/api/v1/statements/verify?hash=4a5e8f..."
```

#### Successful Verification Response (`200 OK`):
```json
{
  "valid": true,
  "status": "GENUINE_OFFICIAL_DOCUMENT",
  "issuer": "Tokenized RWA Marketplace Official Document Authority",
  "keyId": "rwa-statement-signer-v1",
  "hash": "4a5e8f...",
  "verifiedAt": "2026-10-18T20:00:00.000Z"
}
```

#### Tampered or Forged Document Response (`422 Unprocessable Entity`):
```json
{
  "valid": false,
  "status": "TAMPERED_OR_INVALID",
  "error": "The statement hash or signature could not be verified against the official issuing authority."
}
```

### Method B: Offline Hash Verification

To verify that a downloaded PDF file matches the hash provided by the user or statement headers:

```bash
# Compute the SHA-256 checksum of the received PDF
sha256sum statement_2026-05_USER123.pdf
```

Compare the resulting hash against the `X-Statement-SHA256` header or submit it to the `/verify` endpoint above.
